# 送审后·客户批注处理 与 交付前自检（股权类/工程类通用收尾环节）

> 报告初稿交付后，客户（评审方）常返回一份带批注/修订痕迹的稿。这一节把"处理批注 → 落实修改 → 交付前自检"的完整流程沉淀下来。这是每单都会走的收尾环节，与范式无关。

## 一、动手前先查既定口径（改任何正文前必做）

**动手改任何正文前,先查两处历史记录**:①项目记忆/口径记录里已定的核心口径;②过程稿/目录下最近几版修改说明 md。命中已拍板内容——无论'必须保留'还是'必须删除'——不得凭本轮批注/修订自行反向操作,除非新指令明确说推翻此前口径。接续会话/compact 后重新接手时这条尤其致命:冷启动容易把定过的事再判一遍、判反。(血泪:某版把委托方微信已定调必须保留的某投资管理办法句当空断言误删,下一版返工恢复。)

## 二、批注分三类对待（别一刀切，更别把要求理解窄）

客户批注按处理方式分三类：

1. **措辞类**（用词不准、病句、口径措辞）→ 直接改。例：客户纠正"服务对象排的是生活污水不是生产废水"，就把"生活与生产污水混流"改成"生活污水混流"。
2. **数据/口径类**（金额、口径、总投资取哪个数）→ **先跟用户确认口径再改**，别自己拍。口径常常是分层的（概况章用预算口径、投资控制章用概算口径），别为了"统一"把两个各有出处的数改成一个。
3. **需专业判断类**（评价结论、成功度打分、风险评估）→ AI 不下判断，留「（供评估师核定）」标记，由评估师定稿。

### ⚠️ 血泪教训：批注要求"写明细/写对比/展开"时，别猜一个最省事的版本

客户批注说"某处要写明细"或"概算及结算的明细都写上"这类，**极易理解窄**。真实翻车记录：
- 客户要"1.5 项目总投资展开三口径对比"，第一次只改了正文文字、**漏改了下面那张表**（表还停在只列概算明细）。
- 客户再说"概算及结算的明细都写"，又把它理解成"结算只写个审定总数"，**没拆结算明细**。

**固化规则**：批注出现"明细/对比/展开/都写上"这类扩展性要求时——
- 先把客户原话拆成"要哪几个维度、每个维度要拆到几级"；
- 正文改了，**对应的表格/附件也要同步改**（别只改文字漏了表）；
- 拿不准拆多细，**列选项问用户**（"结算明细是拆成送审/核减/核减率，还是按费用科目分部分项/措施/其他/规费/税金拆？"），别自己选个窄的交上去；
- 用户说"越细越好"就往最细挖（去原始造价报告抠费用构成/单位工程明细）。

### ⚠️ 批注说"删除/冗余/去掉"时，先确认删除范围到"节"还是到"句"

批注措辞短(如'这一出感觉冗余,建议删除')不代表范围小。判断法:锚点挂在节标题或段落群起始时,优先假设指整个可独立成篇的逻辑单元(整节),不是锚点那一句。动手前先框出该逻辑单元起止边界、列出待删范围清单;拿不准就问'确认是删整节还是只删这句'。(实战教训:一条'这一出'实指某整节十余段,差点只删一行。)

## 三、回复客户批注的技术操作（docx 批注线程内逐条回复）

- 在客户批注线程内逐条回复：是否认同 / 为什么 / 怎么改 / 改了什么。
- python-docx 无 add_reply，要手写 4 个 XML 部件（comments/commentsExtended/commentsIds/document）。
- **大坑**：清 run 改文本会吞掉夹在 run 间的 commentReference（锚点还在但图标+回复挂载点没了）。修法=在 commentRangeEnd 后重插一个带 CommentReference style 的 commentReference run。

### 回复批注 ≠ 修改标记批注,一轮交付两者都要
带批注版里有两类我方批注,缺一不可:①**回复批注**——挂在评审每条批注下(paraIdParent 挂链),答"您的意见怎么处理的";②**修改标记批注**——锚在**每个正文修改点**上(顶级批注),写「修改说明:改了什么+依据(具体文件文号/批注原文)」。只做①不做②=评审翻正文看不出哪里被改过、凭什么改——固定规矩本来就是"每处修改锚批注:改了什么+依据",别再只顾回复线程漏了修改标记。自查法:列出本轮 vs 来稿基线的全部正文 diff 点,逐点核"有没有一条批注锚在这说明它"。

## 四、去批注 / 去修订痕迹 / 去作者元数据（交客户前出干净版）

**先分清两个不同的东西**——客户说"把批注去掉"可能指的是修订痕迹，不是批注：
- **批注（comment）**：批注气泡。侧栏显示评论文字。
- **修订痕迹（tracked changes）**：审阅模式下的插入/删除标记，侧栏显示"删除:XXX""插入:XXX"。**这不是批注**。

### 去批注（comment）
docx 是 zip。要连锚点+部件+引用一起清，只删 comments.xml 会让 Word 报"需修复"：
1. document.xml 里删所有 `<w:commentRangeStart>`/`<w:commentRangeEnd>`/承载 commentReference 的 run（注意：run 里若同时有正文 w:t，只删 commentReference 子元素、保留文字）。
2. 删 4 个部件：comments.xml / commentsExtended.xml / commentsExtensible.xml / commentsIds.xml。
3. 清引用：[Content_Types].xml 的 Override、document.xml.rels 的 Relationship。
4. 用 zipfile 遍历原包 namelist 保序重打包，跳过删掉的部件。

> ⚠️ **批注锚点嵌在 `<w:del>` 里时，简单"接受修订"会连锚点一起丢**（曾有一条批注中招）。若某条批注的 `commentRangeStart`/`commentRangeEnd` 或 `commentReference` 恰好被包在一段 `<w:del>`（被删文本）内，直接 accept 修订会把整个 w:del 删掉、批注锚点随之消失，批注就悬空了。**修法：先把该批注重锚到相邻保留段（如"待补充纪要"处），再 accept 修订**。动手接受修订前，先扫一遍 `commentRangeStart/End` 是否落在任何 `<w:del>` 内层，命中的先重锚。

### 去修订痕迹（accept all revisions）
> ⚠️ **必须扫全部关联 part，不能只处理 document.xml**（曾栽在这：只 accept 了 document.xml，漏了 footnotes.xml，成品里整整残留一条"口径说明…"脚注的 3 处 w:ins，被复核揪出返工）。修订痕迹可能藏在：`word/footnotes.xml`、`word/endnotes.xml`、`word/header*.xml`、`word/footer*.xml`。**动手前先 `grep -l 'w:ins\|w:del' word/*.xml` 列出所有含痕迹的 part，逐个 accept，别默认只有正文有。**

用 lxml 按命名空间处理 document.xml **及上述每个含痕迹的 part**：
- `<w:ins>`：unwrap（去标签留内容）。
- `<w:del>`：整个删除（连 delText，被划掉的字彻底消失）。
- 所有 `*Change`（pPrChange/rPrChange/sectPrChange/tblPrChange/tcPrChange/trPrChange）：删标记本身、保留父级。
- `<w:moveFrom>` 删、`<w:moveTo>` unwrap。
- 清 settings.xml 的 `<w:trackChanges/>` 免得再次以修订模式打开。
- 等价于 Word "审阅→接受→接受所有修订"。**注意**：accept 会让审阅人的删改真正生效（被删的话真没了），动手前跟用户确认是否全部接受、有没有想保留的删除项。

### 去作者元数据
- 删 word/people.xml（批注作者署名，如各评审人真名）+ 清它在 rels/Content_Types 的引用。
- 若有 tracked changes 的 w:author 属性也一并抹（改空或统一名）。

## 五、金额溯源（每个数追到原始证据文件）

客户或存档要求"标数据来源"时，把报告每个金额追溯到**最初出自哪份原始证据文件**（不是报告第几段）。

### 读扫描件 PDF 的可靠办法（踩坑结论）
原始证据 PDF 大多是**扫描件、没有文本层**：
- `pdftotext -layout` 先试，只有少数原生文本层的能抽出（如某些会议纪要）。
- 扫描件抽不出。`tesseract` 在沙箱下读 /tmp 图片会被拦、识别率也差。
- **可靠办法 = `pdftoppm -r 200 -png` 把关键页渲成图 + 多模态视觉直读印刷体金额**。逐字比对，比 OCR 可靠。
- 关键页定位：造价报告找"工程造价汇总表/费用计算程序表/单位工程造价汇总表"（一般在报告前20页）；会议纪要找决议项；合同找"签约合同价"条。

### 溯源表模板
输出一张表：| 口径 | 金额(元/万元) | 数据来源文件 | 完整路径 | 佐证(PDF页码+逐字原文片段) | 备注 |
- 每个金额附从 PDF 逐字读到的印刷体/手写原文当铁证，不凭"应该来自XX"推断。
- 同一金额多源的做交叉核实（如概算在会议纪要+审批表+请示呈批表三源）。
- 挖不到直接出处的**如实标"存疑/未检索到"**，别编来源。
- 常见"表述差异"要标清但不算存疑：源文件笔误（如"319865.4万元"多个万字）、计算值（核减率是两个金额算出来的、报告没直接印）、某数在某报告里不复述（概算在结算报告里不复述）。

## 六、交付前自检清单（定稿前必过，八类）

任何投后评价报告交付客户前，扫这八类问题（可派 agent 生成一张《人工审核清单》）：

- **A 待填占位符（必清）**：全文搜"供评估师核定/待定/待补充/【】/××/XX/(注:"，以及"半句没写完的病句"。**只要还留着"供评估师核定"字样就不能交付**。
- **B 数字核对**：所有金额出现位置汇总；核减链复算（核减额=送审−审定？核减率=核减÷送审？每个百分比反推算式）；有没有冒出第三个总投资口径值；控制价/预算等勾稽关系算不算得平（算不平先查是不是原始文件"定死的数"而非该算出来的，是的话属措辞问题非错）。
- **C 客户敏感事实项**：单位名/项目名/地点/编号/署名逐字核（客户自己最清楚，错了最丢人）；服务对象、排水性质等被客户纠正过的措辞是否已收窄。
- **D 结论自洽**：结论方向与数字方向一致（核减=投资控制好，结论不能说超支）；成功度打分权重和是否为1（残缺指标集算出的分不是最终分）。
- **E 环境/社会效益不编造**：环保整改类效益**定性写"达到环保要求"**，材料没有的量化数据（分流率/COD/水质提升）**绝不编造**；报告若自己交代"量化材料未归档"是诚实处理。
- **F 第三方立场（评估机构 ≠ 被评价对象，别滑成"自评"）**：评估机构是独立第三方，报告全篇描述被评价对象（委托人/建设单位）时必须用**第三方外部视角**称谓——首次出现用**公司全称**，之后用"该公司/建设单位/委托人"；**严禁**裸称"公司"或用"我司/我们/本公司"，那会让文本读起来像被评价对象在自我表扬，破坏评估独立性/客观性。**效益评价、社会责任、对外形象这类带褒扬色彩的段落最容易踩**（主语一含糊就从"第三方客观评价"滑成"当事人自评"，评审必圈）。交付前 grep 全文裸用"公司"逐处核立场，注意别误伤：泛指（"上市公司供应链验厂"）、其他单位全称（施工/造价/评估机构）、制度性词组（公司法/公司章程）都不动，只改"裸指被评价对象"那种。（曾栽过：社会效益章"维护公司文明绿色形象/体现公司履行社会责任"四处裸称，被评审批注"公司全称"。）
- **G 批注结构完整性(每次带批注版交付前必核,缺一不可)**:①原批注条数:交付版原批注数=客户来稿原批注数,一条不少,逐条列编号核对;②每条原批注下必有一条我方'回复批注'(commentsExtended 的 paraIdParent 挂链到父批注末段 paraId),无回复=未处理完;③每个正文修改点必有一条'修改标记批注'(写明改了什么+依据),拿本轮 vs 来稿基线的全部正文 diff 点逐条核对锚没锚;④计数关系:原批注数=回复批注数,修改标记批注数≥本轮实质修改点数。任一对不上,禁止交付。(血泪:某版把评审 5 条原批注删剩 1 条零回复,被定为铁律;同轮又漏了修改标记批注。)
- **H 双口径删除审查(审任何带 w:ins/w:del 的 docx 时必做,是禁止交付的硬门槛)**:只用"接受修订后"单口径比对,会先把 w:del 内文字抹掉再比,导致整块被标记删除的内容(整节/整表/附件清单)在视图里等于不存在、永远不作为差异冒出来——本单就这样漏看了"第9章11条附件列表被客户删除",人工翻 Word 才发现。故凡文件含 w:ins/w:del,下结论/交付前必跑两个口径:
  - **口径A（接受修订后全文）**:剔除所有 w:del 内文字后的最终态,与锁定基线逐段比对——查静默改动、查最终会变成什么。(实现见本节"验收方法"里 lxml 剔 w:del 那条。)
  - **口径B（全删除块清单）**:用 lxml **单独遍历所有 `w:del`（及 `w:moveFrom`）元素**,按 part(document/footnotes/endnotes/header/footer)、作者(w:author)、时间(w:date)聚合,逐块列出:删了什么文字、谁删的、所在段落/表格位置、连续块长度(连续几段/几个单元格)、是否含标题/整表/附件项/批注锚点(commentRangeStart/End)。
  - **硬规则**:口径B 里凡**标题级 / 整表 / 附件清单 / 连续多段**的删除,一律逐条人工写处理结论(采纳/驳回/待确认),**不许只报字数**。任一大块删除未写结论,禁止交付。
  - **产物落盘**:口径B 清单存成文件(如《删除块清单.md》)作为审核留档的一部分,与带批注版一起归档。
  - 附注(实战教训作背景):发现一大批 w:del 来自**我方评估师旧标记**而非客户本轮,多半是**客户用了旧底稿**、内容已在我方定稿版处理过——别当客户主动删,回原始来稿对齐 w:author/w:date 分清是谁哪一轮删的再定处理。
- **I 报告正文只留结论,禁写内部推敲过程(交付前必扫,读者视角红线)**:报告正文是给评审/客户看**结论和事实**的,不是给他们看"我方内部如何想通某个口径/如何取舍两套算法"的推导过程。把内部推敲话语写进正文=读者看不懂、显得自己没算明白、还给评审送靶子。
  - **判据**:写进正文的每一句自问"这是给读者的**结论/事实**,还是我方**推导它时的思考过程**?"——后者一律删,包括"××与××分属两套算法不宜混用""为避免混淆特此说明""经内部核对/口径消化如下""上述XX元系……以区别于YY"这类。
  - **正文留**:最终口径/数值是多少、以哪个为准、差异用一句话点明来源即可(如"审定数XX,与对比表毛口径YY相差ZZ,主要源于……口径不同,本报告以XX为准")。**删**:多个中间数的来龙去脉、我方如何取舍、算法A vs 算法B 的对比推敲。
  - 需要留痕的内部推敲放**批注/修改说明/过程稿**,不进正文。
  - 与 F 类(第三方立场)、与 skill 述标线"禁内部计分语言上页"同源:**内部工作语言(计分/推敲/口径消化)一律不进交付正文**。(实战血泪:某版 1.5 节把"××元毛口径增加额与××万净口径分属两套算法不宜混用"整句写进正文,被截图反问"这段在说什么?我看不懂",返工简化为一句"以审定施工图预算××万为准"。)
- **K 上报/汇总类报告禁给上级编"资金安全总结论"(源材料查无实据即为捏造,交付前必扫)**:把多个项目的完整版评价报告汇总成一份"向上级(国资监管部门等)履职汇报/年度专项报告"时,极易为了"给上级一个资金安全交代",在总体情况里自行拔高出一句强断言——如"未突破投资授权""未发生国有资产流失和重大减值""无资金挪用/超概算支付"。**判据**:凡带"国有资产流失/重大减值/投资授权/资金挪用/超概算"这类资金安全强断言的句子,回三份(或N份)源材料完整版**逐份检索**——查不到对应结论或专门测试(如"是否发生减值"的判断)=**无据文案,必须删或改弱**。改法:换成源材料和范式模板都用过的中性措辞"未发现重大风险"(这个各版完整版都有、有据)。**根因**:"程序合规"推不出"没发生资产流失/减值"——后者是要专门做过测试才敢下的结论,汇总时凭空加=给上级送假背书,最危险。**分寸参照**:范式模板(投资主体自出的同类专项报告)也只写"不存在重大风险"这种轻措辞,从不写"未发生国有资产流失",照它。(实战血泪:某多项目汇总专项报告提纲为"给上级资金安全背书"加了"未突破投资授权、未发生国有资产流失和重大减值",reviewer 拿各完整版全文检索均查无实据,判无据文案返工,改为"均在批复的概算及授权额度范围内实施,未发现重大风险"。)
- **J 派 reviewer 的清单必含"读者视角审查",别只给技术项(协调者派活红线)**:reviewer 只审你清单里列了的东西。清单只写技术正确性(数字对不对/结构闭不闭合/痕迹干不干净),它就只查技术项,**可读性问题(冗余、重复、啰嗦、内部推敲、评审看不看得懂)一条查不出**——不是它失职,是没让它看这个。故派任何"审给人读的产物"的 reviewer,清单分两大块:
  - **A 技术正确性**:数字复算/批注结构/口径分层/删除审查/包完整性(即本节 A-I 各类)。
  - **B 读者视角(必给,缺=清单不完整)**:拿纯读者视角**通读接受态全文**(不是抽查改点,重复/冗余常跨段),查①和别处重复/讲同一件事②啰嗦绕口、一句话能说清的绕成一段③内部推敲/工作语言上了正文(I 类)④评审/客户看不看得懂。
  - 协调者自查:主 agent 脑子里装着全文,派活时就该主动说"别和 X 段重复";reviewer 拿干净上下文单看文件、未必知道哪段和哪段讲同一件事,得在清单里点明"通读查是否与既有段落重复"。(实战血泪:某版 1.5 节写的差异说明段和客户已有段落讲同一件事、明显重复,但给 reviewer 的清单七八条全是技术项、漏了读者视角,reviewer 技术项全 PASS、重复漏网,被一眼看出反问"为什么 review 没查出来"。)

### 验收方法（每步都要实测，别信"改好了"）
- ⚠️ **比对"带修订痕迹"的 docx 文字,禁用 python-docx 的 `paragraph.text` / `cell.text`**——它静默跳过 `w:ins` 包裹的 run(不报错不警告),会把基线里真实存在的修订插入内容误判成"下游编造"(实战血泪:某版验收 reviewer 就这样把委托方亲手 w:ins 插入的《投资管理办法》名称错判为无中生有,险些打回正确成果)。正解:lxml 遍历段内/单元格内全部 `w:t`,祖先链含 `w:del` 的剔除、其余(含 w:ins 内)保留,得到"接受修订后"文字再比对。
- ⚠️ **核数据源(引另一份完整版当汇总/引用的原始材料)时,表格里的评级/打分/金额若被修订标记包裹,`cell.text` 会读成空——必须穿透 w:ins/w:del 读表**。场景:做"汇总报告/专项报告引用完整版数据"这类活,拿完整版当铁证逐格核评级(成功度打分表)、财务表时,若完整版是 WPS/Word 带修订追踪存的,`table.rows[i].cells[j].text` 会把整张评分表读成一片空白(内容全在 w:ins 里),误判成"源材料没有这个评级/这张表=汇总稿捏造"。**判据**:核完整版任何表格前,先测该 docx 有没有 w:ins/w:del(`'w:ins' in tbl._tbl.xml`);有就用 lxml 遍历 cell 内全部 `w:t`(剔 w:del、留 w:ins)取真值,别信 `cell.text` 的空结果就下"查无此数"结论。**另注**:同一张评分表可能有"旧版被整体 w:del 删除 + 新版 w:ins 插入"两套并存(如旧 XX 分表被删、新 XX 分表插入),核评级要认**接受修订后的最终态**(w:ins 那套),别把被删的旧分当现行值。(实战血泪:某多项目汇总,reviewer 核各完整版成功度评级,几张打分表 cell.text 全空,穿透 w:ins 才读到真分,否则会误判汇总稿"优秀"评级无据。)
- **grep 全部 part（不止 document.xml）**确认 commentRangeStart/End/Reference 或 w:ins/w:del/delText 计数为 0：`for p in word/document.xml word/footnotes.xml word/endnotes.xml word/header*.xml word/footer*.xml; do grep -c 'w:ins\|w:del' $p; done`。只查 document.xml 会漏脚注/尾注/页眉页脚里的残留（这是一次返工的直接教训）。
- unzip -l 确认部件删净、grep 所有 rels+Content_Types 无残留引用。
- **python-docx 逐段比对原文**：段落数相等、"文字有变化的段落"清单只限预期那些（证明没误伤别处）、表格单元格数不变。
- **原地更新前先备份**（.bak/.bak2...），能回退。
- ⚠️ 用户可能打开错文件：改在"无批注版"上，用户却打开旧"带批注版"看，以为没改。交付时明确告诉用户用哪个文件名，必要时帮他关旧窗口重开。

## 七、处理评审批注:反推真实需求,用我方证据做增量,严禁复述邀功

评审常"边批注边自己动手修订"——她改出来的往往只是**骨架示范**(定性形容词,无日期无文件),批注(如"并未做具体分析")的真实需求是**要我方拿证据链把骨架做实**:每条归因落到"环节+时间段+文件出处",这是证据在我方手上、评审做不了的活。两个连环坑:①把评审自己的修订复述回去当"已补充/已落实"——她一眼看穿"你只是在重复评估师的话";②只"确认采纳"不做增量——等于没干活。正确流程:看 w:ins 的 w:author 分清该处谁改的→**反推批注背后她缺什么**(通常缺证据实化/量化/出处)→用证据库把它补实→回复里写清"您的框架+我方做实了什么"。回复没有增量=活没干完,不是措辞问题。

## 八、每版修改必出"带批注版"（固定规矩）

每一轮修订（无论批注驱动还是补充材料驱动），交付物固定两件：**干净修订版 + 带批注版**（在干净版上把每处修改锚 Word 批注），外加一份修改说明 md 存过程稿。

- 批注文本格式：「本轮修改：<一句话改了什么>。依据：<哪份材料哪处>」，从修改说明提炼，不整段照抄。
- 批注作者统一"【机构评估】"。
- 锚点粒度：一处实质修改一条批注；同段多条改动合并一条说清；删除类锚在相邻保留段上、写明"此处原有××已删及原因"。
- 工艺：comment.py 生成 comments 系 XML → document.xml 加 commentRangeStart/End（必须是 w:r 的兄弟节点）+ CommentReference run → pack。只加标记不动正文 run。
- 自检：带批注版与干净版正文 diff 零差异；批注锚点/线程按下面两类分开校验，别把"全量 comments 数 = 正文锚点数"当规则（回复批注是靠 paraIdParent 挂在父批注上的线程、本就没有独立正文锚点，混算会自相矛盾）：
  - **顶级批注（有正文锚点的那种）**：每条校验 commentRangeStart / commentRangeEnd / commentReference 三者成对且 id 对应无孤儿。
  - **回复批注（走 commentsExtended 的 paraIdParent 线程、无独立正文锚点）**：每条校验有有效的 paraIdParent 挂到父批注末段的 paraId（不校验它有正文 RangeStart/End）。
  - **计数关系**：客户原批注数（顶级）= 保留的顶级原批注数（一条不少）；每条原批注恰有一条我方回复批注；每个实质修改点 ≥ 一条修改标记批注。

## 九、交接包做完后：项目文件每更新一次，同步更新交接包对应文件

项目做到一定阶段，可能整理一个**给客户内部复用的交接包**（典型结构：01_最终报告 / 02_支撑材料 / 03_评分与依据 / 04_方法论[人读复用指南 + AI-skill 副本] / 05_交接说明）。交接包一旦建成，它就成了主线的一份"下游镜像"——**主线任何文件更新，都要同步更新交接包里对应的那一份，别让交接包停在某个旧版就交出去一份过期的东西**。

同步判据（改完主线任一类文件，回头对交接包过一遍）：
- **报告定稿件更新**（又出了新一版 V、带批注版/预览版变了）→ 换掉 `01_最终报告/` 里的对应 docx。
- **支撑材料/证据增删**（客户又补了原始件、某份作废）→ `02_支撑材料/`、`03_评分与依据/` 同步增删。
- **评分表/口径/金额链变动**→ `03_评分与依据/` 的溯源表 + `04_方法论/复用指南.md` 里引的实例数据（总分、档位、投资链金额）一起改，别只改报告漏了指南里的举例。
- **skill 本身更新**（章节骨架/口径话术/自检清单/本 reference 改了）→ 重拷一份进 `04_方法论/AI-skill原件/`，**且每次重拷都要重跑那道"挑私货"**（删掉别客户数据/别范式文件/.DS_Store，只留工程类通用 + 本单料），别把新加进 skill 的其它项目私货又带进客户包。
- **人读指南定稿**（从"初稿·待定稿后校"转正）→ 去掉 `【初稿·待定稿后校】` 标记，并按最终口径校一遍数据。

判据一句话：**交接包 = 主线的镜像，不是一次性快照**。每轮主线改完，末尾多问一句"这次改的东西，交接包里有没有对应的一份也该改"，有就一起改、别拖到下次。
