# 从"完整版投后评价报告"提炼"后评价专项报告"（下游流程）

## 这篇管什么（先分清和主流程的关系）

skill 主流程做的是：散乱资料 → **完整版**投后评价报告（股权类四章/工程类七章，几十页）。
**这篇管的是再下游一步**：把一份或多份**完整版报告**，压缩提炼成**《后评价专项报告》**——
投资主体报送**上级/集团/国资监管**的浓缩说明（10 页量级，五节骨架）。

一句话判据：
- 客户给你**原始资料**要出正式报告 → 走主流程（完整版）。
- 客户给你**已经做好的完整版报告** + 一份《专项报告》模板，要"提炼成模板的样子" → 走这篇。

两者关系：专项报告是完整版的"执行摘要 / 报送版"。数据、结论全部来自完整版，**不新增任何
数据和判断**，只做"提炼 + 立场转换 + 排版对标模板"。

## 专项报告的五节骨架（对标客户模板，固定结构）

```
标题：《[投资主体]关于[项目名]投资后评价工作专项报告》
      （若是年度汇总多项目版：《[投资主体]XXXX年度投资后评价工作专项报告》）

一、后评价工作总体情况
    —— 评了哪个/哪几个项目、类型、决策性质、投资额预算vs实际、一句话总评
       （达没达预期、有无重大风险）

二、项目后评价具体情况
   （一）项目概况         —— 建设/投资内容、地点、规模、背景
   （二）项目决策情况      —— 「1、项目决策情况」决策过程 + 「2、项目决策评价」
   （三）项目实施情况      —— 「1、投资建设计划与实际对比」+「2、实际投资额与计划投资额对比」(带对比表)
                            +「3、项目建设质量」+「4、资金用途」
   （四）经营效益情况      —— 股权类：财务与经济效益（营收/净利/现金流 vs 可研）
                            工程类：环境合规效益，无财务测算，用造价链对比表

三、存在的问题及原因剖析   —— "问题+原因"配对，逐条列
四、应汲取的经验教训       —— 可复用的管理教训
五、下一步工作重点         —— 整改举措

附件：1.《[完整版报告全名]》（报告文号）
      2.后评价项目对比表        ← 附件2 统一命名口径（见下）
落款：[投资主体全称] / [报送日期]
```

- **一份完整版 → 一份独立专项报告**（除非客户明确要年度汇总多项目合一）。
- **股权类 vs 工程类的差异只体现在（四）经营效益节和问题节**：股权类有财务测算表、
  工程类是环境合规效益无财务回报。其余四节结构一致。
- 附件2 的对比表**统一叫「后评价项目对比表」**（客户定的口径），不要各项目
  各叫各的"XX项目主要经济指标对比表"。附件1 保留完整版报告全名+文号。

## 核心红线（提炼时逐条守，交付前逐条自查）

### 1. 立场转换：第三方评估口吻 → 投资主体自述口吻
完整版是评估机构（**第三方**）写的，通篇"该公司/受托方/评价机构认为"。
专项报告是**投资主体自己报送**的，口吻要转成**投资主体自述视角**——但两个都不许：
- **不许出现第一人称**"我司/本公司/我们"。用"[投资主体名]/公司/该项目"。
- **不许残留第三方口吻**"投后评价机构认为/评价机构/受托方"——那是完整版的说话人，
  专项报告里投资主体不会以评估机构口吻说话。
判据：全文 grep "我司/本公司/我们/评价机构/受托方/评估机构"，命中即改。

### 2. 占位符绝不编造
完整版里的未填占位符（形如"营收【】""关联方应收账款【待确认】""××地区【】"）是原报告
没填完的坑——**提炼时跳过该句、不引用该数据**，用"经营覆盖范围与可研测算口径存在差异"
这类概括语带过，**绝不编一个数字填进去**。宁可少写一句，不可造一个数。

### 3. 问题节口径：按项目真实成色写，不拔高也不掩盖
- 优秀项目（评级优/良）：问题节写**轻度改进项**（如"营收未达可研预期，因口径差异"），
  **别为了对标模板里那个失败项目而把小改进拔高成硬伤**。
- 失败/部分失败项目：照实写硬伤，别掩盖。
- 判据：问题的严重程度 = 完整版结论里的真实严重程度，不受模板案例影响。
  （模板本身可能是个失败项目——子项目终止、投资仅完成 XX%——但你手上的项目未必，
  别被模板的"问题级别"带跑。）

### 4. 禁内部计分语言上正文
完整版里的"得分/扣分/满分/XX.X分/XX分/权重/指标分值"是内部评分表语言，
**专项报告正文不搬**。总评只说"评定等级优秀/良好"即可，不写具体分数。

### 5. 禁 AI 味 / 对仗腔 / 互联网黑话
"赋能/抓手/闭环/双轮驱动/倒逼"一律不用。完整版原文若有（曾遇原文出现"双轮驱动"），
提炼时改成朴实说法。中文去 AI 味走 humanizer-zh skill 的清单。

### 6. 数字溯源
每个引用的金额/日期/比例/占比，都要能在完整版里找到原句，不得杜撰、不得算错。
提炼是"搬运+改写句子"，不是"重新计算"。

### 7. 项目专属敏感口径以本项目历史为准
每个客户/项目可能有自己踩过的雷（如某工程客户曾明确删过"监理"表述）。
接同类活先查该客户的专属口径 + 项目记忆，别重复引入已被删的词。

### 8. 落款统一
落款主体 = 投资主体（用其工商登记全称），**不是完整版的评估机构**。
日期 = 报送日期（默认当天，不确定就问）。

## 排版对标模板：先量准，再落地（这是重点，别凭经验定字号）

客户给的模板 PDF 是"长什么样"的唯一标准。**绝不凭经验/惯例假定字号字体**（第一次就栽在
这：凭经验做成五号仿宋12pt，模板实测是三号仿宋15.9pt，整整小了一号半，全部返工）。

### 第一步：用 pymupdf 逐字量出模板真实字体/字号/行距
`pip install pymupdf`（venv 里装）。量三样：①各文本块的字体名+字号（按字符数统计众数，
最高频的就是正文/标题各自的规格）②页面尺寸+页边距（bbox 极值反推）③正文行距（同列相邻行
baseline 间距的众数）。用 pymupdf 的 `page.get_text("dict")` 遍历 span 取 font/size/bbox 统计即可。

**关键：字体名要以模板实测为准，不要想当然。** 模板里 pdffonts 能列出内嵌字体
（`pdffonts 模板.pdf`），如 FangSong/SimHei/KaiTi/方正小标宋(FZXBSJW)。用户手改后的
基准 docx 字体名也要实测——曾遇到用户在 Word 里选的宋体存成了非标准名"SimSong"，
就得一字不差照它设，别自作主张改成 SimSun。

### 第二步：把实测规格落进 python-docx（几个必踩的坑）

**坑1：中西文必须分开设字体**，否则数字/年份会变成仿宋很难看：
```python
from docx.oxml.ns import qn
def set_font(run, cn='仿宋_GB2312', en='Times New Roman', size=16):
    run.font.size = Pt(size)
    rpr = run._element.get_or_add_rPr()
    rf = rpr.get_or_add_rFonts()
    rf.set(qn('w:ascii'), en); rf.set(qn('w:hAnsi'), en)   # 西文数字
    rf.set(qn('w:eastAsia'), cn)                            # 中文
```

**坑2：字号存不进的会被截断。** Word 字号按 0.5pt 步进存储，模板实测 15.9pt 存不进去会被
截成 15.5pt（偏小）。**按中文字号的标准磅值落地**：三号=16pt（Word 能精确存），别硬塞 15.9。
落地后回读确认没有 15.5 残留。

**坑3：行距用固定值 EXACTLY，不是倍数。** 公文正文行距是固定磅值：
```python
from docx.enum.text import WD_LINE_SPACING
pf.line_spacing_rule = WD_LINE_SPACING.EXACTLY
pf.line_spacing = Pt(28)   # 三号字配28磅固定值（示例，按模板实测值填）
```

**坑4：按段落文字前缀判断层级，套对应字体。**
⚠️ 下表的 16pt 是**某模板实测为三号**的结果，不是通用常量。**新项目先量出自己模板的正文
是几号**（四号=14pt、小三=15pt、三号=16pt…），再把全表字号按对应磅值整体替换，别照抄 16pt。
| 段落特征 | 字体 | 字号(=三号16pt示例) | 加粗 | 缩进 |
|---|---|---|---|---|
| 文档主标题（第0段） | 以基准 docx 实测为准（曾遇模板内嵌是 SimSun，但用户手改基准存成非标准名 SimSong，照 SimSong 设、别纠正成 SimSun——这俩不是同一个名） | 二号22pt | 粗、居中 | 无 |
| 「一、二、三、四、五、」中文数字+顿号 一级标题 | 黑体 | 三号16pt | **看模板**（曾遇用户手改成不加粗） | 无 |
| 「（一）（二）（三）（四）」二级标题 | **楷体_GB2312** | 三号16pt | 否 | 无 |
| 「1、2、3、4、」阿拉伯数字+顿号 三级标题 | 仿宋 | 三号16pt | 是（加粗） | 无 |
| 正文叙述段 | 仿宋_GB2312 + 数字Times | 三号16pt | 否 | **首行缩进=2×正文字号磅值，随字号联动（16pt→32pt），别记死32** |
| 附件条目「1.《…》」「2.…」 | 仿宋 | 三号16pt | 否 | 看模板 |
| 落款两行 | 仿宋 | 三号16pt | 否 | 右对齐、无缩进 |

**判层级的坑**：区分「一、」（中文数字，一级标题）和「1、」（阿拉伯数字，三级标题）时，
判据用"首字是**中文数字[一二三四五六七八九十]** 且 第2字==顿号"，绝不误伤「1、2、」三级——
它俩加粗/字体规则不同，误判会连锁改错。**别把范围钉死在"一~五"**：年度汇总多项目版
（《…XXXX年度…专项报告》）一级标题会出现「六、」「七、」甚至更多，钉死五就会把第六节起
判成正文、套错字体。若某客户模板一级用「（1）（2）」括号数字，判据另按该模板实测调整。

### 第三步：表格样式（美观口径）
- 客户常嫌默认 Normal Table 的细网格"像虚线"。改成**全框线实线**：给表加 `w:tblBorders`
  六条边（top/left/bottom/right/insideH/insideV）全 single、黑色、sz=6（=0.75pt）。
- **所有单元格文字上下（垂直）居中**：`cell.vertical_alignment = WD_CELL_VERTICAL_ALIGNMENT.CENTER`
  （逐格设，不是只首格）。表头行文字水平也居中。
- 表头行原件常自带 sz=12 的粗上下边框（三线表粗表头），**默认保留**（更突出、也美观），
  除非客户要"全表统一细线"。表格文字字号小五10.5pt。

可直接复制的落地代码：
```python
from docx.oxml.ns import qn
from docx.oxml import OxmlElement
from docx.enum.table import WD_CELL_VERTICAL_ALIGNMENT

def set_table_borders(table, sz=6, color="000000"):
    tblPr = table._element.tblPr
    old = tblPr.find(qn('w:tblBorders'))
    if old is not None: tblPr.remove(old)
    borders = OxmlElement('w:tblBorders')
    for edge in ('top','left','bottom','right','insideH','insideV'):
        e = OxmlElement('w:'+edge)
        e.set(qn('w:val'), 'single'); e.set(qn('w:sz'), str(sz))
        e.set(qn('w:space'), '0');    e.set(qn('w:color'), color)
        borders.append(e)
    tblPr.append(borders)

for table in doc.tables:
    set_table_borders(table)                       # 全框线 sz6 黑色
    for row in table.rows:
        for cell in row.cells:
            cell.vertical_alignment = WD_CELL_VERTICAL_ALIGNMENT.CENTER   # 逐格垂直居中
```
（表头行的 sz12 粗上下边框若要保留，就别用上面循环覆盖表头那两条 tcBorders；本单是保留的。）

## 施工令怎么派（多 agent 纪律，本单踩过的坑）

- **写码/改格式全派子 agent，我只监督**（铁律9）。但**施工令必须把"禁转包"写成硬判据**：
  "你必须在自己进程内直接写 Python 动手，**禁止调用 Agent 工具、禁止调用 Task 工具派子 agent、
  禁止转包，违反即返工**"——只写"不得转包"这种软措辞约束不住，agent 照样往下再派一层
  （本单表格美化那轮就被转包了）。
- **改完必派独立 reviewer**（reviewer 类型，只审不改）核，审的人不能是改的人、也不能是
  转包链的一环（铁律12）。reviewer 施工令同样要写死禁转包。
- **每批改动前先备份**（.bak/.bak2/.bak3 递增，别覆盖），万一改坏可回滚。
- **用户手动改了某一份当基准时**：先只读实测它改成了什么（字体名/加粗/字号），把其余份
  **对齐到这个实测基准**，别拿自己之前的规格去覆盖用户的手改。
- **"只改格式不动文字"的批次，reviewer 必须逐段与备份比对文字**：曾有表格美化那批（本该
  只动表格 XML）被转包的 agent 顺手把正文一句"一定程度上影响了"改成了"一定程度影响"
  ——格式批次悄悄改了文字。所以①施工令写死"除表格XML外一个字不动正文"，②reviewer 核验
  必含"与 .bakN 逐段文字比对，除授权改动外零差异"这条，别只核格式属性。文字红线比格式更
  容易被"顺手优化"破防。

## 交付前自检清单（逐条打勾，任一不过就返工）

结构与内容：
- [ ] 五节骨架齐全（总体/具体〔概况+决策+实施+效益〕/问题/教训/下一步/附件/落款）
- [ ] 立场转换：`grep "我司\|本公司\|我们\|评价机构\|受托方\|评估机构"` 零命中；**且通读一遍**
      确认主语立场真转成投资主体自述——grep 只逮词，删掉"评价机构认为"后若留下被动句仍是
      第三方视角，语义残留 grep 逮不到，必须人眼过一遍（呼应"reviewer 必含读者视角审查"）
- [ ] 占位符未编造：`grep "【\|待确认"` 零命中（占位符符号确定，能机检）；完整版的
      【待确认/【】】未被填入杜撰数字
- [ ] 问题节口径与项目真实成色匹配（优秀项目=轻度改进项，未拔高成硬伤）
- [ ] 无内部计分语言（得分/满分/具体分数/权重）上正文
- [ ] 无 AI 味/黑话：`grep "赋能\|抓手\|闭环\|双轮驱动\|倒逼"` 命中即改；中文去 AI 味走 humanizer-zh
- [ ] 数字溯源：每个金额/日期/比例能在完整版找到原句
- [ ] **附件2 对比表每格数据与正文、与完整版一致**（新造汇总表，易和正文脱节）
- [ ] 项目专属敏感词已规避（如某工程"监理"，`grep "监理"` 零命中）
- [ ] 附件2 统一命名「后评价项目对比表」；附件1 保留完整版全名+文号
- [ ] 落款 = 投资主体全称 + 报送日期

排版对标模板：
- [ ] 正文字号/字体/行距 = 模板实测值（不是凭经验，且无 15.5 之类截断残留）
- [ ] 中西文分开设（eastAsia=中文体、ascii/hAnsi=Times New Roman）
- [ ] 各层级标题字体正确（一级黑体、二级楷体、三级仿宋加粗，别互相误伤）
- [ ] 表格：全框线实线、单元格垂直居中、表头水平居中、表头粗线按客户口径
- [ ] 多份之间格式一致：**用 python-docx 读各份 run 的字体/字号做集合比对，差异即不一致**
      （别肉眼扫；同批处理才能保证一致）

流程：
- [ ] 每批改动派了子 agent（施工令含禁转包硬判据）
- [ ] 改完派了独立 reviewer 核（审者≠改者≠转包链）
- [ ] 交付前给用户看了效果（docx 直接 Word 打开 / 或转 PDF 图对比模板）

送审后（若客户/上级在报送版上批注返回，走这条）：
- [ ] **逐条回复客户批注**（铁律13）：保留全部原批注一条不少，每条下挂一条我方回复批注
      写清"是否认同+怎么改/为何不改"。交付前数一遍：原批注条数=现存原批注条数，且每条有回复。
      具体做法（含 XML 四文件联动挂回复批注）见 `reference/送审后批注处理与交付自检.md`。
