# 成功度细化评分 + 外部审核意见处理

## 一、客户要求"专家打分法 + 更细指标"时

1. **先拍板"专家是谁"，再动手**。第三方报告里出现"专家评分"列，评审必问专家名单和打分原件。两条路让委托方/评估师选：
   - 路线 A（默认推荐）：方法名写「综合评分法（参照专家打分法思路细化指标体系）」，评分列叫「评分」，评分主体是评估机构项目组，全文不出现"专家"字样；
   - 路线 B：评估机构出 2-3 名评估师真名，各出一张署名打分表放附件。**严禁凭空虚构专家**。
2. **细化表设计工艺**：
   - 指标体系按报告章节映射设计（前期决策/招投标合同/建设实施/投资财务/效益目标/可持续性），不硬套客户样例里的设备类指标（供货周期、减员增效之类）；
   - **反推配分锁住既有总分**（权重合计=1.00，加权合计精确=原总分）——避免总分漂移引发 7.2/摘要/结论连锁改动，这是实务惯例不是造假，前提是低分必须落在报告已认定的真实短板上（未编可行性研究、工期滞后、效益缺量化、施工事故等），分布才可信；
   - 每行"评分依据及扣分说明"只能出自报告既有事实，逐行过一遍红线扫描（客户/外部给的表格文字不可信，见下节）；
   - 指标数适度：样例 15 项、我们用了 24 项，再多每行都是被追问依据的口子；两行含义重叠（如"过程资料完整性"vs"档案归集完整性"）要改写出区分或合并；
   - "待委托方补充"这类内部待办不能写进交付表格，改"据委托方说明"口径。
3. **改方法句别弄丢既有依据引用**（真栽过）：原 7.1 引导句引用了《（地方国资主管部门）…后评价工作指引（试行）》——四档制划分的出处。整句替换前先盘点原句里的文件/制度引用，并入新句保留。凡施工令写"改为：xxx"的整句替换，主 agent 必须先读原句再放行。
4. 数学自检：权重合计=1.00、逐行加权分=权重×评分（两位小数）、总分精确等于既有分、正文叙述沿用原口径（如"XX.X分"），表格合计单元格才允许出现"XX.X0"。

## 二、外部审核意见（codex 等）的处理流程

1. **逐条验真再动手**：外审说"缺出处"的，先回原始 PDF 查——曾遇外审称某项签证/变更金额无溯源，实际全在《结算审核报告》第 10 页汇总表里，处理从"删行"变成"补页码引用"。接受/半接受/驳回逐条记录进修改说明。
2. **外审给的施工令不能照抄**，必须主 agent 修一遍再派：
   - 它拿的是过期状态（说批注 42 条，实际已 48 条）——数量类断言全部按当前文件实测重写；
   - 它会违反自己列的红线（自检清单要求"可研"清零，建议文本里却写着"可研论证"）——外来文本一律重跑红线扫描；
   - 补上我们自己的工艺要求：禁转包、施工前备份+记 md5、批注锚点保护、完工后主 agent 独立验收。
3. **每条意见判归四档分流（处理外审意见的骨架，先分档再动手）**：外审意见不是逐条照单全改，先给每条判档——
   - **A档＝成果稿能直接改的**：无据表述、选择性披露（只报有利口径、藏了不利事实）、AI 味/宣传腔、措辞过满的定性。这类在成果稿正文直接改。
   - **B档＝挂批注给评估师/客户的**：涉及**原始铁证（完整版/一手材料）内部矛盾、需一手证据才能核清的事实死结**（如报告出具日期倒挂、同一事项在正文与表格里日期/数值打架）。**不硬改成果稿去"抹平"矛盾**——那是拿成果稿替铁证的所有方（评估师/客户）背锅；正确做法是在成果稿对应句上挂批注，讲清矛盾+请对方以一手证据核清。批注 author 填"编制组"（我方主动提请核实、单层问题批注，不是回应对方的批注，不需回复线程结构）。
   - **C档＝暂留的**：依赖别的前置才能做的（如某字段依赖日期先核清）、及纯格式类。前置没到位就先不做，别硬凑。
   - **D档＝不采纳的**：超出本报告体例、把报告拔高成不该有的东西（如给汇总/上报报告硬加"整改台账"责任人/期限/考核指标，或要求原始铁证方另出清洁稿）。不采纳的要一句话说清为什么。
   判据自查：动手前先给外审每条标 A/B/C/D，B 档尤其别误判成 A 去硬改——问一句"这矛盾是成果稿的表述问题，还是铁证本身的问题？铁证的问题就挂批注、不硬改"。
4. **同一诉求在多处重复出现时，施工易只改第一处、漏掉后面的（本单栽过，reviewer 才逮出，施工自报全 PASS）**：一条外审诉求（如"把过满的合规定性软化成事实陈述"）在正文里常有**多个落点**（段首一处、段尾又一处；不同项目节各一处）。施工 agent 习惯改掉最显眼的第一处就报完成。
   - **施工令要点名"全段/全文扫，别只改第一处"**：把该诉求所有落点用唯一字符串逐个列进施工令，别只给一个定位串。
   - **reviewer 验收要 grep 计数验残留**：对"要清除/软化的表述"grep 全文，计数必须=0 才算改净；不能只看施工 agent 报的"已改"。
   - 配套：软化定性形容词（"完整/规范/合法合规/完备"）时，保留后面列的事实（日期/文号/程序），只去无保留的定性帽子；别把事实一起删了。

## 三、docx 表格整表替换的手术要点

1. **删旧表前必查批注锚点**：旧表 XML 范围内若有 commentRangeStart/End/commentReference，必须成对迁到邻近保留段落，否则批注变孤儿。删前 grep 确认为 0 也要留证。
2. 宽表工艺：7 列长说明表用 9pt（w:sz 18）、表布局 autofit 改 fixed 锁列宽、说明列约 43%、一级维度列 vMerge 合并、表头跨页重复。
3. 批注内部时间戳（w:date/dateUtc）不许写未来日期，跟文件名同规矩。

## 四、验收脚本自身的坑（误报先怀疑脚本）

1. `<w:t[^>]*>` 会误匹配 `<w:tcPr>`/`<w:tcW>`/`<w:tbl>`——必须用 `<w:t(?:\s[^>]*)?>`。用错正则会同时制造"两版正文不等"和"表格解析为空"两个假阳性。
2. 表格数学复算时，两位数序号会被 `\d{2}` 当成评分——按列位取数，别按"哪个单元格长得像分数"取。
3. 原则：独立验收脚本报红，先用最小样本（打印一行原始 cells）验证脚本，再下"产物有问题"的结论。
4. **比对两版正文一致性，别用正则啃 `<w:t>`**——非贪婪 `<w:t...>(.*?)</w:t>` 在整篇 XML 上会跨标签失控、吞掉大段源码，制造假的字符数差异（本单栽过：84634 vs 84702 全是假的）。正确做法：`xml.etree.ElementTree` 解析、遍历 w:t 节点取 .text 拼接再比。
5. **每次改动必派独立 review agent 复核，只当协调者**：审的人≠改的人≠协调者自己。自己跑脚本自审不算独立 review。曾有 reviewer 抓到两处"信息放错行"（把11月的控制价审议接在4月立项格、合同签订实际格塞开工/竣工的计划数据），都是主 agent 自审时没发现的真错位——对比表/对照表尤其要逐格问"这格的信息是否只属于本阶段"。

## 五、交付物版本命名

文件名里的数字是**真实日期**，严禁用未来日期递增编号（"0715 事件"）。同一天出多版：日期+版本号后缀（如 `修订版0713-V2`）。修改说明 md 同步改名、内文引用同步替换。

## 七、计划vs实际对比表（进度评价常用）的硬规矩

客户曾明确批评并勒令："计划列每格必标数据来源，实际列必写实际完成时点"。对比表的命脚就是逐项比时间/指标，缺来源和缺时点等于没对比。
1. **"计划/依据"列每一格都要带来源标注**（〔基建中心某报告〕/〔招标文件〕/〔施工合同〕），不许裸写"2021年4月底完成"这种无出处计划值——评审必问"计划哪来的"。
2. **"实际"列每一格都要有实际完成时点**，不许裸写"已完成"。有确切日期写日期；材料无确切日期的（如勘察/设计交付日），写"开工前完成（…；具体日期材料未载）"，不硬编月份——同不编造红线。
3. 破折号"—"格填内容后要清干净，别留残破折号。做完 grep 每列确认无裸"已完成"、无残"—"。

## 八、客户一条意见里常含多个诉求点，别只改好改的那一半

一条口头/微信意见里往往塞了 2-3 个独立诉求，容易只抓最显眼、最好改的那点交差，漏掉其余（曾栽过"一条意见含多诉求只改一半"）。
1. **收到意见先拆成逐点清单**：把一句话里的每个独立诉求单列一行（如"社会效益那段软化 + 补主动整改的正面定性"是两点，不是一点）。
2. **对报告逐点核**：每点回到报告对应位置确认是否已落实，落实一条勾一条，全勾才算这条意见闭环。
3. 别用"我改了其中最关键的一点"糊弄——客户列的每点都是验收项，漏一点就是没做完。

## 九、改造前后对比缺硬数据时，软化成"风险隐患"口径，别硬编对比数字

进度/效益/社会效益章节要写"改造前 vs 改造后"对比，但手头常没有改造前的量化基线（如投诉次数、溢流频次、达标率）。
1. **缺基线数据时不硬编对比值**（"改造前年投诉 30 次降至 5 次"这种没出处的数字是评审必删项，也踩造假红线）。
2. **改写成定性的风险隐患口径**：把"改造后投诉减少"软化为"改造后有助于降低……溢流/投诉/环境风险"——讲趋势和机理，不编具体降幅。
3. 本单财务效益（规避罚款/停产损失）同理：客户拿不出测算依据就只做定性风险描述，不写省了多少钱。
4. 与第八条配套：软化的同时若客户另有正面事实（如主动整改、超前完工），补进去做正面定性平衡，别只剩风险口径。

## 十、第9章附件清单只列手头真有原件的，缺的进批注；判断有没有必须解开 rar/zip 核

附件清单是评审逐项核对原件的索引，列了却拿不出原件比不列更糟。
1. **只列手上确实有原件的附件**，逐项对应到素材库里的真实文件（PDF/扫描件/Excel）。
2. **清单里出现但手头没有原件的**，不许硬列充数——改为在带批注版里加一条批注说明"此件委托方未提供原件，定稿前需补"，交给评估师去催。
3. **判断"到底有没有这份附件"必须解开压缩包核**：素材常打包成 rar/zip，光看外层文件名会漏判（本单附件从 5 项补到 11 项，就是解开压缩包后才发现里面还有可列的原件）。不解压就断言"没有"是盲判。

## 十一、同名资料常有"空模板"和"已填写"两份，引用出处要点到填过的那一份

委托方给的资料里，同一份表常同时存在一张空白模板和一张实际填过数据的，文件名可能几乎一样。
1. **引用出处前先确认引的是填过数据的那份**，不是空模板——批注/正文里写"据《提供资料情况明细表》"要指向真有内容的那份。
2. 本单批注 49 的出处就从泛指改精确为"据委托方填报的《提供资料情况明细表》"，"填报的"三字锁定是已填写版，避免评审翻到空模板质疑出处不实。
3. 解压核对（第十条）时就顺手区分：同名多份按"是否已填内容"分辨，别按文件名先后或大小猜。

## 六、给评估师的交接提醒写法

转给第三方的提醒必须自带背景（他们没有聊天记录上下文），并把口子分成两类说清：
- **等数据的口子**：写明"拿到数据怎么改、拿不到怎么改"两个预案（如投诉记录：有→补量化进 5.2；无→删句或软化成"有助于降低…投诉风险"）；量化财务效益（规避罚款/停产损失）必须客户提供测算依据并书面确认，否则只能定性；
- **报告已覆盖不用等的**：点名已写全的位置（如政策时限 vs 实际完工的时间链、五值造价链），免得对方重复索要。
